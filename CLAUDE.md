# SudokuPlay

A playful sudoku web app (PWA): Vite + React + TypeScript.

## Architecture
- `src/engine/` is the sudoku engine: pure TypeScript, no React or DOM imports. Keep it that way, so it stays testable and can move to a native app later.
- Grids are `Uint8Array(81)` in row-major order, `0` = empty. Candidates are 9-bit masks (`candidates.ts`).
- The UI and animation layer only react to engine output: `applyAction(state, action)` in `game.ts` returns the next state plus `GameEvent`s in a fixed order (documented at the top of the file). Game rules never live in components; animations hang off events, not off state diffs.
- Animations live in `src/animation/`: `choreograph(events)` (pure, tested) turns events into timed cues; `CuePlayer` plays them with the Web Animations API on elements found by `data-cell`, `data-note-digit`, `data-pad`, `data-control` and `data-board`. Things already gone from the state (erased digits, removed notes) are animated as ghosts in the board's fx layer; the finale's confetti is a canvas there too (`confetti.ts`). Effects animate only transform, opacity or box-shadow and each has a reduced-motion version (`effects.ts`).
- In development, the dev panel under the board previews every animation without changing the game and has a tempo control (slow motion) for tuning. Timing lives in `effects.ts` (durations) and `choreograph.ts` (delays and staggers).
- Styling: every colour, radius, shadow and font is a token in `src/styles/tokens.css` (light and dark); component styles live next to their component (`Board.css`, …) and use only tokens. `tokens.test.ts` checks WCAG AA contrast for every text/background pair, so add new pairs there. Animation colours are tokens too (`--fx-*`), resolved by the cue player. Fonts are self-hosted via `@fontsource-variable` so the PWA works offline.
- Points: `scoring.ts` in the engine turns game events into a score plus awards (pure; rules at the top of the file). Hints: `hint.ts` picks the cell (selected cell, else the next logical placement); the `Hint` action locks the cell. The session keeps score and play time and passes awards to the animation layer with each batch. In development, `ScoreBreakdownPanel` shows `scoreBreakdown` live beside the board: points per reason and what solving now would add (`solveAwards`, shared with the real finale so the projection always matches).
- Statistics: finished games (solved, or abandoned after a move) are stored in localStorage on this device (`src/stats/`, versioned key, defensive parsing). `summarize` is pure and tested; the stats page lives at `#stats`.
- Randomness in the engine is always seeded, so puzzles and tests are reproducible.
- Difficulty = the hardest human technique `gradePuzzle` needs (`logic.ts`, easiest first). The same `LogicStep`s will drive hints.
- The app gets puzzles from `createPuzzle` (`puzzleBank.ts`): a bank puzzle picked by seed plus a random validity-preserving transform. The generator is too slow for expert puzzles at runtime, so it only runs offline.
- `src/engine/puzzleBank.generated.ts` is generated by `npm run build:bank` (deterministic, about a minute). Never edit it by hand; rerun the script after changing the generator, grader or techniques.

## Checks
- Check command: `npm run check` (ESLint, type check of app and config, all Vitest tests). Run it once before saying work is done.
- CI (`.github/workflows/ci.yml`) runs `npm run check` and `npm run build` on every pull request and on pushes to main.
- Tests are Vitest, next to the code as `src/**/*.test.ts`. Puzzle fixtures live in `src/engine/__fixtures__/`. Use `fast-check` for properties that must hold for any puzzle.

## Git
- Work in a worktree under `.claude/worktrees/`, never in the main checkout. Install dependencies there only.
- Conventional commits, branch names `feat/...`, `fix/...`, `refactor/...`.
