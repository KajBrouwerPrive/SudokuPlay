## Escalation filter
### Generic
<!-- baseline:escalation-filter -->
- Before you decide something, check it against the escalation filter. The design, the fixed rule names and the table "Settings" with the values are in `baseline/escalation-filter.md` in the control repo. Read the values there every time; never copy one into a ticket, a PR or this file.
- A decision is a choice between at least two realistic options that changes the result: behaviour, structure, scope, data model, dependencies, or something hard to undo. A step that a rule prescribes, a choice the owner already made in the ticket, the brief or the chat, and a choice without effect outside the change are not decisions: do not record them.
- Check the escalation rules in the order of the table under "Escalation rules: the owner decides" in that document. The first rule that applies settles it. If one applies, or you cannot tell whether one applies (`doubt`), stop on that choice and put it to the owner; do not decide it yourself and do not work around it.
- If no escalation rule applies, decide yourself and record it with the `record_decision` tool of the `issues` MCP server, before you open the PR. Give the question, the signature from the list "Question signatures", at least two options, the choice, the reason, and the basis from the table under "Bases for deciding itself: the agent decides and records". Use the names exactly as the document writes them. The tool checks again what is deterministic and refuses a self-decision that an escalation rule hits; then the choice goes to the owner after all.
- Before `gh pr create`, as a fixed step: go through the diff and list every choice in it that is a decision by the definition above. A description of the choice in the PR body does not count as recording it. For each one: no escalation rule applies, so call `record_decision`; or a rule applies or you doubt, so put it to the owner and wait for the answer. Only open the PR when none is left.
- A choice the owner already made (in the ticket, the brief or the chat) is not recorded, but it is made visible: list it in the PR body under the fixed heading `## Keuzes van de eigenaar`, one line per choice, each with a reference to the ticket or the brief that holds it. The Claude review does not report a choice under that heading as an unrecorded decision. Never use the heading for a choice you made yourself.
- The PR body gets a section `## Besluiten`, generated by the IssueTracker GitHub App from what you recorded. Never write or edit it by hand. A decision you took but did not record is reported by the Claude review as an unrecorded decision. Record it, or put it to the owner, in a fix like any other review finding.
- Never put a secret, a token, personal data or a customer name in `question`, `options` or `reason`: the tool refuses the whole row. An unattended run has no `issues` server and writes its decisions as `baseline/autonomous-runs.md` describes.

## Risk class label
### Generic
<!-- baseline:risk-class -->
- Every ticket you create or pick up carries exactly one risk class label: `R0`, `R1`, `R2` or `R3`, next to its kind label (`Feature`, `Improvement`, `Bug` or `Task`). The dispatcher starts a run only when the class of the release equals this label, and `record_decision` reads the expected class from it. What happens to a decision without it is described in the section "Risk class" of `baseline/escalation-filter.md` in the control repo.
- Set the label with `save_issue` when you create the ticket. For a ticket you pick up without a class label, set it before you start. The labels are the class names themselves; never invent another label, never set two.
- Determine the class from the files the work will change, with the rules of the merge verdict (IssueTracker `docs/workboard.md`, "Risicoklassen") and the section "Risk class" of `baseline/escalation-filter.md` in the control repo. Fixed floors: every change in `Pro-Solutio/control` and every change to `.claude/settings.json` is `R3` (constitution); a change under `supabase/migrations/` is at least `R2`. The class of a ticket is the highest class of any change it needs.
- In doubt between two classes, take the stricter one. Never lower a class to make a run or a decision easier.
- If the scope changes so that the class changes, update the label (`save_issue` with the full label set, the kind label included) and say so in a comment on the ticket.
- Only the owner lowers a class set by the owner.

## Architecture
- `src/engine/` is the sudoku engine: pure TypeScript, no React or DOM imports. Keep it that way, so it stays testable and can move to a native app later.
- Grids are `Uint8Array(81)` in row-major order, `0` = empty. Candidates are 9-bit masks (`candidates.ts`).
- The UI and animation layer only react to engine output: `applyAction(state, action)` in `game.ts` returns the next state plus `GameEvent`s in a fixed order (documented at the top of the file). Game rules never live in components; animations hang off events, not off state diffs.
- Animations live in `src/animation/`: `choreograph(events)` (pure, tested) turns events into timed cues; `CuePlayer` plays them with the Web Animations API on elements found by `data-cell`, `data-note-digit`, `data-pad`, `data-control` and `data-board`. Things already gone from the state (erased digits, removed notes) are animated as ghosts in the board's fx layer; the finale's confetti is a canvas there too (`confetti.ts`). Effects animate only transform, opacity or box-shadow and each has a reduced-motion version (`effects.ts`).
- In development, the dev panel under the board previews every animation without changing the game and has a tempo control (slow motion) for tuning. Timing lives in `effects.ts` (durations) and `choreograph.ts` (delays and staggers).
- Styling: every colour, radius, shadow and font is a token in `src/styles/tokens.css` (light and dark); component styles live next to their component (`Board.css`, …) and use only tokens. `tokens.test.ts` checks WCAG AA contrast for every text/background pair, so add new pairs there. Animation colours are tokens too (`--fx-*`), resolved by the cue player. Fonts are self-hosted via `@fontsource-variable` so the PWA works offline.
- Points: `scoring.ts` in the engine turns game events into a score plus awards (pure; rules at the top of the file). Hints: `hint.ts` picks the cell (selected cell, else the next logical placement); the `Hint` action locks the cell. The session keeps score and play time and passes awards to the animation layer with each batch. In development, `ScoreBreakdownPanel` shows `scoreBreakdown` live beside the board: points per reason and what solving now would add (`solveAwards`, shared with the real finale so the projection always matches).
- Statistics: finished games (solved, or abandoned after a move) are stored in localStorage on this device (`src/stats/`, versioned key, defensive parsing). `summarize` is pure and tested; the stats page lives at `#stats`.
- Randomness in the engine is always seeded, so puzzles and tests are reproducible.
- Difficulty = the hardest human technique `gradePuzzle` needs (`logic.ts`, easiest first). The same `LogicStep`s will drive hints.
- The app gets puzzles from `createPuzzle` (`puzzleBank.ts`): a bank puzzle picked by seed plus a random validity-preserving transform. The generator is too slow for expert puzzles at runtime, so it only runs offline.
- `src/engine/puzzleBank.generated.ts` is generated by `npm run build:bank` (deterministic, about a minute). Never edit it by hand; rerun the script after changing the generator, grader or techniques.
